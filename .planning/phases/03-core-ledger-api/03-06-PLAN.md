<objective>
TDD implementation of the account routes: POST /v1/accounts (create), GET /v1/accounts/:id (read with balance), and GET /v1/accounts/:id/postings (cursor-paginated posting history).

Purpose: Accounts are the foundation of the double-entry ledger. The balance field comes from account_balance (materialized by the Phase 4 balance worker — will be 0/null in Phase 3 tests). The pagination route depends on the postings.created_at column added in Plan 02 (Wave 1), which is why this plan depends on 03-02. Completing these routes closes API-07, API-08, and API-09.

Output: accounts.ts route plugin + accounts.test.ts integration tests. server.ts updated to register accountRoutes.

IMPORTANT: GET /v1/accounts/:id returns balance from the account_balance table. In Phase 3 the balance worker (Phase 4) has not run, so account_balance rows may not exist. The route must handle a NULL balance gracefully — return '0' (string) as the balance when account_balance row is absent, since no postings have been processed by the worker.
</objective>

POST /v1/accounts:
  Method: POST
  URL: /v1/accounts
  Body: PostAccountBodySchema { type: 'asset'|'liability'|'revenue'|'expense'|'equity', metadata?, owner_ref: string }
  Success: 201 + { id: string (uuid), type, metadata, owner_ref, created_at }
  Error: 422 if type not in enum, or owner_ref missing

GET /v1/accounts/:id:
  Method: GET
  URL: /v1/accounts/:id
  Params: UUIDParamSchema { id: string }
  Success: 200 + AccountResponseSchema { id, type, metadata, owner_ref, created_at, balance: string, balance_updated_at? }
  Not found: 404 { error: 'Account not found' }
  Balance handling: LEFT JOIN account_balance; if no row → balance = '0', balance_updated_at = null

GET /v1/accounts/:id/postings:
  Method: GET
  URL: /v1/accounts/:id/postings
  Params: UUIDParamSchema { id }
  Querystring: PaginationQuerySchema { cursor?: string (ISO-8601), limit?: integer 1-100 default 50 }
  Success: 200 + PostingsPageResponseSchema {
    data: PostingResponseSchema[],  ← amount_cents is string
    next_cursor: string | null      ← last item's created_at as ISO-8601 if data.length === limit, else null
  }
  Not found: if account doesn't exist → 404 (or empty data[], your choice — simpler is 200 with empty data)

Cursor pagination query (using postings.created_at from migration 0010):
  SELECT id, transaction_id, account_id, amount_cents, direction, created_at
  FROM postings
  WHERE account_id = $id
    AND (cursor IS NULL OR created_at < $cursor)  ← keyset: less-than for DESC order
  ORDER BY created_at DESC
  LIMIT Math.min(limit ?? 50, 100)

  next_cursor: if results.length === effectiveLimit → results[results.length-1].created_at.toISOString()
               else null

Drizzle equivalent (see RESEARCH.md Pattern 7):
  db.select()
    .from(postings)
    .where(and(
      eq(postings.account_id, params.id),
      cursor ? lt(postings.created_at, new Date(cursor)) : undefined
    ))
    .orderBy(desc(postings.created_at))
    .limit(effectiveLimit)

Drizzle insert for accounts (accounts is NOT append-only — standard insert allowed):
  await db.insert(accounts).values({ type, metadata, owner_ref }).returning()

Drizzle LEFT JOIN for GET /v1/accounts/:id:
  await db.select({ ...accounts, balance: accountBalance.balance, balance_updated_at: accountBalance.updated_at })
    .from(accounts)
    .leftJoin(accountBalance, eq(accounts.id, accountBalance.account_id))
    .where(eq(accounts.id, params.id))
    .limit(1)
  → result[0] or undefined (404); balance may be null (account_balance row missing) → return '0'

BigInt serialization note:
  accountBalance.balance is bigint({ mode: 'bigint' }) → JS BigInt in query result.
  The registered BigInt serializer converts it to string in the HTTP response automatically.
  Do NOT manually call .toString() on the balance before send — let the serializer handle it.
  However, when balance is NULL (no account_balance row), return the string literal '0' in the response body.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP querystring → pagination query | cursor and limit params from untrusted clients reach Drizzle query |
| HTTP request body → accounts INSERT | User-supplied type/metadata/owner_ref written to DB |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-06a | Denial of Service | GET /accounts/:id/postings unbounded limit | mitigate | PaginationQuerySchema maximum:100 + belt-and-suspenders Math.min(limit,100) in handler; limit>100 → 422 by Ajv |
| T-03-06b | Tampering | SQL injection via cursor param | mitigate | cursor passed as new Date(cursor) then fed to Drizzle lt() which parameterizes as $N; never string-interpolated into SQL |
| T-03-06c | Tampering | account type constraint bypass | mitigate | TypeBox Type.Union([Literal('asset'),...]) enforced by Ajv before handler; DB CHECK constraint as belt-and-suspenders |
| T-03-06d | Tampering | Path traversal via account id | mitigate | UUIDParamSchema format:'uuid' — Ajv rejects non-UUID before handler |
| T-03-06e | Information Disclosure | NULL balance in response | accept | Returning '0' for absent account_balance is correct behavior (no balance worker in Phase 3); no sensitive data disclosed |
</threat_model>
