  Success: 200 + TransactionResponseSchema body
  Not found: 404 { error: 'Transaction not found' }

post_transaction call pattern (from RESEARCH.md Pattern 3 + PATTERNS.md shared patterns):
  Signature: post_transaction(p_idempotency_key text, p_description text, p_source text, p_metadata jsonb, p_postings posting_input[])
  Returns: uuid (transaction id)
  Each posting_input: ROW(account_id, amount_cents, direction)::posting_input
  Call via: db.execute(sql`SELECT post_transaction(${key}, ${desc}, ${'api'}, ${metadata}::jsonb, ARRAY[ROW(...)::posting_input, ...])`)
  Amount_cents in ROW must be passed as BIGINT — coerce from number: BigInt(posting.amount_cents)

Idempotency handling (RESEARCH.md Pattern 6):
  RECOMMENDED: SELECT transactions WHERE idempotency_key = $1 BEFORE calling post_transaction.
  If found: return 200 + existing transaction.
  If not found: call post_transaction → returns winner's tx_id → return 201.
  Concurrent race: if the SELECT misses but post_transaction's internal race handler fires,
    the handler still returns the winner's tx_id → fetch and return 200.
  HTTP status detection: if the tx's idempotency_key was present in SELECT (existing) → 200;
    if tx was just inserted (SELECT not found, post_transaction succeeded) → 201.

After calling post_transaction, fetch the full transaction with postings:
  SELECT t.*, p.* FROM transactions t JOIN postings p ON p.transaction_id = t.id WHERE t.id = $tx_id ORDER BY p.created_at ASC

withRetryOnSerializationFailure wrapping:
  The ENTIRE db.transaction({ isolationLevel: 'serializable', ... }, async (tx) => { ... }) call
  must be inside the factory function passed to withRetryOnSerializationFailure.
  Pattern:
    const txId = await withRetryOnSerializationFailure(() =>
      db.transaction(
        async (tx) => { return await tx.execute(sql`SELECT post_transaction(...)`).then(...) },
        { isolationLevel: 'serializable', accessMode: 'read write' }
      )
    )

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP request body → post_transaction SQL | User-supplied postings data crosses the HTTP→PG boundary |
| Idempotency-Key header | Client-supplied deduplication key; not a secret but must be validated |
| ARRAY[ROW(...)::posting_input] construction | Composite type array construction — SQL injection risk if not parameterized |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-05a | Tampering | SQL injection via account_id in ROW literal | mitigate | Drizzle `sql` template tag auto-escapes all scalar parameters as $N bind parameters; each ROW field individually parameterized (not string-concatenated) |
| T-03-05b | Tampering | SQL injection via idempotency_key header | mitigate | idempotency_key passed as Drizzle sql template parameter — never string interpolated into SQL |
| T-03-05c | Tampering | amount_cents integer overflow (BIGINT bounds) | mitigate | TypeBox Type.Integer({ minimum: 1 }) rejects negatives + floats at schema validation layer; PG BIGINT max is 9,223,372,036,854,775,807 — accepted by post_transaction |
| T-03-05d | Tampering | Path traversal via transaction id param | mitigate | UUIDParamSchema with format:'uuid' — Ajv rejects non-UUID strings with 422 before handler is reached |
| T-03-05e | Tampering | Double-entry bypass | accept | post_transaction SQL enforces balance check; CONSTRAINT TRIGGER fires at COMMIT as belt-and-suspenders; both layers outside TypeScript control |
| T-03-05f | Spoofing | Idempotency-Key header forgery | accept | Idempotency-Key is not a security primitive; it is a client-supplied deduplication hint; no secret needed since the ledger itself enforces correctness |
</threat_model>
