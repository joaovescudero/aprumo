    Step 2 — Write content of `packages/core/migrations/0005_audit_triggers.sql`:

    Section A — Generic audit function using EXECUTE format for per-table routing:
    `CREATE OR REPLACE FUNCTION audit_row_change() RETURNS TRIGGER LANGUAGE plpgsql SECURITY DEFINER SET search_path = public AS $$`
    BEGIN:
    `EXECUTE format('INSERT INTO %I (table_name, operation, old_data, new_data, changed_by, changed_at) VALUES ($1, $2, $3, $4, $5, $6)', TG_TABLE_NAME || '_audit')`
    `USING TG_TABLE_NAME, TG_OP, CASE WHEN TG_OP = 'DELETE' THEN to_jsonb(OLD) ELSE to_jsonb(OLD) END, CASE WHEN TG_OP = 'INSERT' THEN NULL ELSE to_jsonb(NEW) END, current_user, now();`
    For UPDATE: old_data = to_jsonb(OLD), new_data = to_jsonb(NEW).
    For DELETE: old_data = to_jsonb(OLD), new_data = NULL.
    `RETURN NULL;` (AFTER trigger return value is ignored by PG)
    END $$;

    Implementation note: use CASE on TG_OP:
    - TG_OP = 'UPDATE': old_data = to_jsonb(OLD), new_data = to_jsonb(NEW)
    - TG_OP = 'DELETE': old_data = to_jsonb(OLD), new_data = NULL
    Never TG_OP = 'INSERT' — trigger is AFTER UPDATE OR DELETE only.

    Section B — Attach triggers to mutable tables (NEVER postings or raw_events):
    `CREATE TRIGGER accounts_audit_trigger AFTER UPDATE OR DELETE ON accounts FOR EACH ROW EXECUTE FUNCTION audit_row_change();`
    `CREATE TRIGGER outbound_endpoints_audit_trigger AFTER UPDATE OR DELETE ON outbound_endpoints FOR EACH ROW EXECUTE FUNCTION audit_row_change();`
    `CREATE TRIGGER outbound_events_audit_trigger AFTER UPDATE OR DELETE ON outbound_events FOR EACH ROW EXECUTE FUNCTION audit_row_change();`

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| mutable table→audit shadow | AFTER UPDATE/DELETE must capture change before data is gone |
| audit function→table routing | EXECUTE format() with table name must use %I (identifier quoting) to prevent SQL injection |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-2-01 | Tampering | audit data integrity | mitigate | SECURITY DEFINER on audit_row_change() prevents caller from bypassing audit; audit shadow tables not writable by aprumo_app (covered by Plan 03 GRANT pattern) |
| T-2-02 | Tampering | schema drift | mitigate | 0005 committed; Plan 09 drift check |
| T-2-03 | Injection | EXECUTE format() SQL injection via TG_TABLE_NAME | mitigate | Use `%I` (identifier quoting) in EXECUTE format() — `TG_TABLE_NAME` is a trigger variable, not user input, but %I prevents edge cases |
| T-2-04 | Repudiation | no audit on postings/raw_events | accept | These tables are append-only; REVOKE prevents UPDATE/DELETE; no mutation to audit |
| T-2-05 | Tampering | test data leakage | accept (Plan 08) | schema-per-file isolation |
| T-2-SC | Tampering | npm installs | transfer | Completed Plan 01 |
</threat_model>
